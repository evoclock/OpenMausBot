# Coding-loop readiness

I want a coding run to reach a verified result, survive a crash without repeating completed work, and leave merging to me. The [seam map](loops-seams-map.md) describes the intended boundaries. This is my ordered list of what remains, not a claim that unattended runs work today. I am handling items 2–8. Item 1 is being delivered in `pi-agentic-driver-agents`.

| Order | Missing step | Where | Smallest unblock |
| --- | --- | --- | --- |
| 1 | Provide a production durable driver API for start, resume, status, report and cancel, with durable step IDs, stable request IDs and reconciliation of uncertain effects. Use the real `@earendil-works/pi-durable` API, not a test adapter or default-off seam in a production path. Reports remain evidence, not completion. | `pi-agentic-driver-agents`, then the public driver package. | I wait for an independently reviewed production API and verified live transport before connecting OpenMausBot. |
| 2 | Finish the public sync path. Stage A on `chore/public-scrub` awaits my decision on a public API rename. Then the reviewed change needs a sync PR to `pi-agentic-driver` and a 1.2.0 release. | `pi-agentic-driver-agents` → `pi-agentic-driver` → package release. | I settle the name, land the reviewed sync and publish the release. Then I confirm the package OpenMausBot imports exposes the production contract. |
| 3 | Connect the real worker and independent reviewer. `server/inner-worker-route.ts` defines `WorkerHost`, but it does not provide a live worker transport. `server/coding-run-runtime.ts` accepts an injected host; production does not instantiate it (`docs/coding-run-composition.md`). | OpenMausBot Stage 2; missing driver operations belong in the driver repository. | I approve the isolated host, working profile, distinct roles and data route. A production host uses the released driver and refuses unavailable routes. |
| 4 | Reconcile and resume an interrupted outer run. `server/outer-runner.ts` currently parks a cut invocation as blocked. Its run snapshot and durable task checkpoint use different databases. | OpenMausBot Stage 2, after items 1–3. | I connect task, iteration and effect IDs across both stores. An isolated kill-and-restart test must show that finished steps are not repeated and uncertain outward actions remain held. |
| 5 | Attach triggers, progress and final delivery to the live server. `server/run-triggers.ts` deduplicates registered occurrences, but `docs/coding-run-triggers.md` says the adapters are not attached to the live scheduler or webhook ingress. Approval answers also need durable correlation and expiry. | OpenMausBot Stage 2. | I register authenticated triggers, wire one result path to the conversation runtime and prove one terminal delivery. No registration means no unattended start. |
| 6 | Bound each coding run. `docs/outer-loop.md` says the runner has no time, spend or iteration budget. A monthly spend cap does not bound one run; changing a model or data route needs an explicit grant. | OpenMausBot Stage 2. | I choose run ceilings and permitted fallback routes; implementation persists counters and stops safely on exhaustion or uncertainty. |
| 7 | Enforce the push destination and draft-PR scope. `server/run-contract.ts` records requested effects, but a classification in a contract cannot prove repository visibility, branch protection or credential scope. | OpenMausBot Stage 3, after Stage 2 merges. | I choose exact repositories, refs and per-repository permissions. The host verifies them before effects, refers to credentials by name only and cannot merge, force-push or publish. |
| 8 | Prove the unattended journey with a deliberate crash. Unit fixtures and a build cannot establish real restart, verification and final delivery. | OpenMausBot Stage 4, after Stage 3 merges. | I run an isolated scripted journey and retain task IDs, revisions, effect receipts, restart evidence and the real-entry verification result. Unknown effects stop the run. |

I will not treat a stored checkpoint as proof that a push or message happened, nor use a fixture transport as a production route. Each stage waits for the preceding stage to merge before its draft PR is ready for integration.
