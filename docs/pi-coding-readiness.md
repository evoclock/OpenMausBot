# Pi coding readiness

A Pi provider instance may set `config.agentDir` to an absolute, reviewed, host-local Pi agent directory. When unset, the driver leaves Pi's agent-directory selection unchanged, including `PI_CODING_AGENT_DIR` if supplied by the host. When set, the directory is passed to the Pi RPC child and used for Pi's settings and local-model catalog. Nothing copies a personal profile or credentials. Every Pi turn requires `poteto-mode-pi` in Pi's `get_commands`, whether or not an agent directory is configured. A missing skill stops the turn before creating its credential-bearing extension file. Skill discovery does not authorize work.

For a bot using Pi, Overview shows the skill and the development and independent-review roles for **that bot's working folder**. The read-only admin endpoint is `GET /api/pi/readiness?botId=<id>`. Place an owner-approved `.pi/pstack-model-roles.v1.json` in that working repository, using schema `pstack-model-roles.v1` and two distinct exact `provider/modelId` identities. A placeholder example is `{ "schema": "pstack-model-roles.v1", "roles": { "development": null, "independent-review": null } }`; replace both null values with approved identities before enabling a coding run. Set `codingRuns.rolesFilePath` to the explicit file path, and set each registration's `developmentRole` and `reviewRole` to the matching identities. Missing, invalid or mismatched roles refuse worker allocation. Keep the file uncommitted: `.pi/` is ignored. `/skill:setup-pstack-pi` is the role-map setup flow; do not infer a model from an example's `null`. The reviewer pool should use current-generation capable models; the implementer pool should use economical models. Check data-route permission and credentials separately: model-list and `set_model` probes confirm Pi discovery and selection, not successful inference, worker dispatch, independent review, or a coding runner.

To connect role setup with bot setup: choose the bot's Pi provider and working repository, run `/skill:setup-pstack-pi` in that repository with owner-approved roles, then open the bot's Settings → Overview to check Pi coding readiness. Use Settings → Soul to review its standing instructions; the bot's `/setup` entry point is a separate flow and is not run by role setup. The canonical Soul value is the bot record (`server/bot-folder.ts`); a private `SOUL.md` mirror lives at `DATA_DIR/bots/<botId>/SOUL.md`, outside the bot-writable workspace. External edits produce drift rather than being automatically adopted. Role-map setup does not edit Soul or grant the bot authority. The owner can describe the desired development and review workflow in Soul, but must separately authorize tasks and effects.

Preflight and role checks use the same Pi RPC commands (`get_commands`, `get_available_models`) as an isolated fixture. Test fixtures use a temporary agent directory and a fake CLI; they do not read the operator's home profile.
