# Coding loops and product seams (Stage 1)

This is the Stage 1 contract map; its missing-seam column records the original gaps, not current readiness. The inner loop is the existing pstack Pi port operated by pi-agentic-driver; this repository must not alter that port. The outer loop adapts Geoffrey Huntley's [Ralph pattern](https://ghuntley.com/ralph/): repeat bounded attempts against a goal, reconcile effects, and stop on independently evidenced completion or an explicit hold. Pi Ralph loop and Cursor `/loop` are behavioral references, not dependencies. Only the owner merges.

## Outer ↔ driver contract to implement

The following is OMB's application protocol. Production now requires a compatible installed driver before running a coding iteration; until the driver change is published and pinned, the attachment remains a draft and the probe refuses startup. The driver source merged `agentic-driver.run.v1` in #51 and #58, but OMB pins only `@earendil-works/pi-durable` 1.4.0 and has no `@evoclock/pi-agentic-driver` dependency. The product owns the immutable run contract (`id`, bot, repository, ref, success criteria and allowed effects in `server/run-contract.ts`) and a durable iteration ledger. The driver owns one invocation intent and its correlated receipt; OMB owns worker and reviewer outputs. A single host owns each SQLite harness; the product does not write the driver's checkpoint. The host must verify the active Pi profile, roles, isolated workspace, repository permissions and credential reference before dispatch (`docs/pi-coding-readiness.md`, `docs/coding-worker-route.md`).

| Operation | Request / result | Restart and idempotency rule |
| --- | --- | --- |
| Start | Outer supplies immutable contract, run ID, iteration ID and stable invocation key; driver returns a durable task identifier or a typed refusal. | Duplicate key with identical input returns the same task; mismatched input refuses. Record task ID before acknowledging start. |
| Resume | Outer supplies task ID and last observed durable step ID after reconciling any uncertain effects; driver resumes only from its persisted committed step. | Never turn `blocked` into `running` solely because a process restarted. A committed step ID is evidence of internal progress, not proof that an external push did or did not happen. |
| Status | Read-only snapshot: task ID, committed step ID, phase, state and last outcome/effect receipt references. | Polling has no execution side effects; version or sequence prevents stale updates from overwriting newer state. |
| Report | Driver supplies correlated iteration/task/step ID, exact revision, scoped evidence and outcome (`progress`, `verified`, `blocked` or failure); outer records one report and delivers progress/final result. | Dedupe by task ID and report ID; require independent verification evidence before `done` (`server/outer-runner.ts`). A receipt or self-report alone is not a verdict. |
| Cancel | Outer sends run/task ID and reason; driver acknowledges stop or reports an already terminal task. | Repeat cancel is safe. Preserve leases and unknown outward effects for reconciliation; no replay after an uncertain cancellation. |

Use the existing `requestId = runId:iteration` and `InnerLoop.invoke(contract, iteration, requestId, signal)` seam (`server/outer-runner.ts`) as the outer-side adapter, not a second scheduler. `server/inner-worker-route.ts` documents idempotent acquisition by request ID, but the actual host must prove it. `server/run-triggers.ts` derives stable IDs for duplicate routine occurrences and signed webhook deliveries. A new iteration needs a new key; a retry of the same iteration retains its key and must first inspect workspace, commit, remote ref and PR state. At the outward boundary, persist intent and receipt with stable effect ID; on missing/ambiguous receipt, park and ask for reconciliation rather than reissuing a push, PR or approval. The two databases in `server/outer-runner.ts` (`runtime.db` and `coding-runs.sqlite`) do not share an atomic commit: reconcile a stored iteration that is ahead of its durable task checkpoint before moving forward.

The package pinned at `@earendil-works/pi-durable@1.4.0` exports `defineTask`, `createRegistry`, `defineExtension` and `Harness` from its root, and `openNodeSqliteStorage` from `@earendil-works/pi-durable/storage/sqlite/node` (`package.json`, `dist/index.d.ts`, `dist/storage/sqlite/node.d.ts`). Its `Harness.open` creates the harness; `Harness.root` returns the conversation; `Conversation.commit` with `tx.createTask` creates a task ID; `Harness.resume` enables scheduling; `Harness.getTask` and `Harness.inspect` read persisted task state; `Harness.waitForTask` waits for terminal settlement; `Harness.abortTask` marks/signals a task for its abort phase (`dist/harness/types.d.ts`, `dist/session/transaction.d.ts`). A phase persists its checkpoint or terminal outcome with `TaskRuntime.commit`, and `TaskRuntime.memo` can store a durable first-writer-wins value (`dist/types.d.ts`). `Harness.resume` is not a per-task resume command: it enables scheduling, and `waitForTask` also enables scheduling. An interrupted phase can run again from its last committed checkpoint; that is why the current adapter parks a previously `running` invocation rather than blindly replaying it (`server/outer-runner.ts`).

The outer runner's `start`, `resume`, `wait`, `get` and `close` are **local wrapper methods**, not pi-durable exports. The installed Pi Durable package has no start/status/report/idempotent-effect protocol for OMB's driver, nor a built-in guarantee that `tx.createTask` deduplicates a caller's run ID: the proposed stable-key lookup, correlated reports, durable external-effect receipts and step IDs require application code. The outer task ID and checkpoint `sequence` are available today; a driver-owned durable step ID is not exposed by this adapter. `Harness.abortTask` exists; its abort signal cancels the attached driver invocation, while uncertain effects still require OMB's checked reconciliation. The driver source provides `openDurableDriver` with start, resume, status, report, reconcile, release, cancel and a required `invokeWorker` transport for one complete inner invocation. Production attaches that transport to OMB's configured worker host. It receives the already-composed goal as opaque text; the ledger and carry text remain OMB-owned. An interrupted invocation stays held and is never replayed. The driver records only the host's correlated result reference; OMB's saved result and effect receipts remain necessary for recovery. The package is not yet published or pinned, so this PR stays draft until the published dependency and offline checks are available. The current published package is 1.4.0; 1.1.2 was not published. It still lacks idempotent `createTask`, per-task resume, effect receipts and driver step IDs. The receipts and reconciliation from [#32](https://github.com/evoclock/OpenMausBot/pull/32) remain necessary. The 1.4.0 SQLite schema v2 migration is one-way: the runner backs up the configured harness database before first open, and rollback below 1.4.0 requires restoring that backup. The integration is locally verified with a package tarball; deployment waits for a compatible published package and the checked effect-recovery host.

Stage 2's isolated kill/restart fixture proved that OMB parks an uncertain outward effect without repeating the worker turn; #20–#22 have merged. That proof does not exercise the separate driver-run API or qualify concurrency. Stage 3 must enforce destination-specific push and draft-PR policy. Stage 4 must exercise a scripted unattended end-to-end run with deliberate crash and evidence. Each stage waits for the preceding stage's owner merge; this document grants none of those effects.
