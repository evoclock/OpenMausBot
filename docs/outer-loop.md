# Outer coding run loop

The run pattern adapts Geoffrey Huntley's [Ralph loop](https://ghuntley.com/ralph/): make one attempt, preserve progress, then start a fresh attempt against the same goal until completion or a stop. The Pi Ralph loop and Cursor `/loop` informed the iteration and stop behavior; no source was copied.

`openOuterRunner` stores a Pi Durable task in a SQLite harness. Each task drives a separately supplied inner-loop adapter. That adapter must run the existing pstack playbook and return its verification result; the outer loop does not duplicate pstack's checks. A progress result starts another iteration, including after repeated reviewer rejection. A verified result with evidence ends the run. Only blocked or cancelled stops the loop without verification. The contract carries an iteration ceiling (`maxIterations`, default 8): a progress result at the ceiling parks the run as `blocked` for owner reconciliation instead of starting another attempt. Unattended runs also require `codingRuns.bots[originBotId]` in operator `config.json`, with positive `maxWallTimeMs` and `maxSpendUsd`. There are no time or spend defaults. Missing limits block before worker dispatch and produce one terminal owner report. `startedAt`, `elapsedMs`, `spentUsd` and spend uncertainty persist in the run snapshot and survive restart. The wall-clock deadline interrupts a running attempt and is rechecked before every iteration. Worker and reviewer turns report priced ledger usage; missing or unpriced usage blocks, never counts as zero. Where the ledger estimates a known model's price, that estimate counts toward the ceiling but can differ from the provider's final bill. A turn can exceed a ceiling before its final usage arrives: this policy stops later work, not the provider's invoice in flight. A status view reports the persisted contract and state.

The production server attaches registered applied schedules and verified webhook deliveries to the WorkerHost. Neither a stored repository classification nor a model verdict authorizes a write: the host must verify destination visibility, token scope, exact per-run external authorization and owner-held effects before it executes anything. This module neither merges nor publishes code. Coding turns disable automatic driver fallback; the server can retry a model only when its exact instance and model are listed in the run's pinned `allowedFallbackModels`. No data-route fallback is implemented; `allowedFallbackDataRoutes` does not by itself activate one. A missing or unlisted route stops rather than silently switching.

The OMB outer runner uses the installed Pi Durable 1.4.0 Harness, not the separate driver-run API merged in the agentic driver source. Its local `start`, `resume`, `wait`, `report` and `cancel` methods are OMB wrappers. A request for the separate `agentic-driver.run.v1` package protocol must pass `requireDriverRunApi()`; it refuses absent or incompatible installed exports. No production coding turn currently calls that package protocol, so this check neither upgrades nor disables the existing OMB runner. The published driver package must be pinned and its transport and effect observations integrated before claiming that bridge works.

Pi Durable stores task checkpoints. Opening an existing harness with 1.4.0 migrates its SQLite schema to v2. The runner backs up `coding-runs.sqlite` from the configured data directory to `coding-runs.sqlite.pre-1.4.0.bak` before opening it, and refuses to open when backup fails. Do not downgrade below 1.4.0 after migration; restore the pre-migration backup instead. Configure `codingRuns.restartLimit` as a positive integer to set the harness crash guard; its default is 5 consecutive interrupted invocations. A sleeping task remains parked until its deadline, whereas a task parked at `restart_limit` needs owner reconciliation, not blind retry. Pi Durable still provides no idempotent `createTask`, per-task resume, external-effect receipts or driver step IDs; retain the receipts and reconciliation from [#32](https://github.com/evoclock/OpenMausBot/pull/32).

The inner invocation has an outward-effect boundary: after the run enters `running`, an interrupted attempt is parked as `blocked` on recovery. It is never automatically replayed. A run that crossed a deadline or spend ceiling while stopped becomes terminal on restart and cannot automatically resume; any new attempt needs a fresh approval through the existing routine approval path. A future reconciliation step must inspect the external state before resuming. Pi Durable's single-storage-owner rule requires one harness owner per database; do not open competing runner processes on the same file. The crash fixture exits during the invocation and confirms recovery parks the run without invoking the adapter again.
