# Coding run trigger boundary

OpenMausBot already schedules cron routines and records webhook deliveries. `startScheduledCodingRun` accepts a persisted scheduled `RoutineRun` after that scheduler marks it running. `startGithubCodingRun` accepts raw GitHub PR and CI event bodies and checks their SHA-256 HMAC before parsing them. Both derive a stable run ID from the persisted occurrence or delivery ID, and return an existing run instead of starting it again after a duplicate callback.

Only owner-configured **private agent repository** templates may start unattended. This boundary rejects external/public templates and external-write grants. The host must independently verify repository visibility, the exact token scope and approved template ownership; a template's `repositoryClass` is data, not proof. Keep the webhook secret outside Git and pass the original raw bytes and `X-Hub-Signature-256` header. Ordinary webhook capability URLs are not a substitute for GitHub HMAC verification.

Operator-registered applied schedules and verified webhook deliveries reach the production WorkerHost through the existing routine scheduler and webhook ingress; the isolated composed-server fixture exercises the scheduled path. A stable trigger ID deduplicates retries, and routine settlement and owner reporting survive restart. Do not open an unauthenticated HTTP endpoint. Existing routine retry and delivery handling remain unchanged.

`server/coding-loop-attachment.ts` is the event-driven seam for that attachment: the scheduler's run-started event calls `scheduled`, and the outer runner's terminal/blocked transitions (observed via `onTerminal` in `server/outer-runner.ts`) settle the correlated routine run exactly once by the stable run id. It owns no timer, no poll and no second scheduler; a terminal report without a live correlation is parked evidence, never a replay. The production server uses its own registered coding runtime and durable routine settlement for this path; this seam remains a fixture contract. Missing per-origin-bot ceilings block an unattended run before dispatch, and a crossed deadline or unpriced spend sends a terminal owner report. An approved new routine is required instead of automatic resume after a crossed ceiling.
